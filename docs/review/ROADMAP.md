> هدف کاربر (۲۰۲۶-۱۱-۱۰): (۱) پست خوب لینکدین، (۲) کد قابل دفاع به‌عنوان نمونه‌کار، (۳) قابلیت تغییر بازه‌ی زمانی و
> ادامه‌ی داده تا امروز برای دیدن روند، (۴) کاربردی‌تر کردن پروژه و جابه‌جایی/نگهداری درست داده.
> مبنا: یافته‌های `FINDINGS.md`. هیچ کدی هنوز تغییر نکرده است.

## ۰. اصل اول: قبل از پست، اعداد باید درست باشند
اعداد فعلی گزارش (به‌خصوص یوتیوب و Event Study) تحت تأثیر C-08، C-09 و C-15 هستند. پست لینکدین با عدد غلط بزرگ‌ترین ریسک است.
اما خود این بررسی یک **داستان خوب** است: «pipeline خودم را audit کردم و دیدم ۴۵٪ داده‌ی یوتیوب بی‌صدا از annotation بیرون مانده بود».

## ۱. تغییر بازه‌ی زمانی تا امروز — الان ممکن نیست، چرا؟
پنجره در چند جا **سخت‌کد** شده («Window Lock» عمدی برای پروژه‌ی درسی):

تا امروز (۲۰۲۶-۱۱-۱۰) یعنی **۳۷ هفته** (۱۶ هفته‌ی جدید از ۲۰۲۶-۰۷-۲۳).

## ۲. آوردن داده تا امروز
| منبع | روش فعلی | سختی | پیش‌نیاز |
|---|---|---|---|
| YouTube | API رسمی (`youtube_extract.py`) | **آسان‌ترین** | `YOUTUBE_API_KEY`؛ اول C-22 (سقف ۵ پاسخ) و C-23 (شکاف watermark) اصلاح شوند، وگرنه داده‌ی جدید هم همان نقص را دارد |
| Reddit | JSON pipeline / Selenium | متوسط | اجرای محلی روی کامپیوتر خودت محتمل‌تر |
| X | Selenium scraper (۳,۴۳۱ خط) | **سخت‌ترین** و شکننده | حساب کاربری، اجرای محلی، ریسک شرایط استفاده |
| مالی | FRED / Yahoo | آسان | `FRED_API_KEY`؛ pin کردن `yfinance` (C-06) |

**Annotation دوره‌ی جدید:** با همان نمونه‌ی طبقه‌بندی‌شده (۱۲۰ رکورد × پلتفرم × هفته) حدود ۳ × ۳۷ × ۱۲۰ ≈ ۱۳ هزار رکورد.
بر پایه‌ی قیمت Pilot گزارش (~$۲۴.۹ برای ۲۳۳ هزار رکورد تک‌Target) یعنی **چند دلار**؛ با سه Target حدود ۳ برابر. (C-20 ممکن است برآورد Pilot را کمی بادکرده باشد.)
**رویدادهای جدید** (بعد از تیر ۱۴۰۵) باید از منابع معتبر به `event_registry` اضافه شوند — کار پژوهشی، نه کدنویسی.

## ۳. کاربردی‌تر کردن
1. **یک دستور، هر بازه:** `python -m src.pipeline.run_pipeline --start 2026-02-28 --end today` — شامل جمع‌آوری افزایشی، annotation افزایشی (فقط رکوردهای جدید)، تحلیل، داشبورد.
2. **حالت دمو:** یک نمونه‌ی کوچک واقعی و ناشناس در ریپو + `make demo` که کل زنجیره را در کمتر از ۲ دقیقه اجرا کند. الان اجرای پیش‌فرض بدون داده‌ی خام در قدم اول می‌شکند و Pipeline B بدون annotation روی `group_comparison` (C-01).
3. **به‌روزرسانی زمان‌بندی‌شده:** هفتگی (GitHub Actions یا cron محلی) برای YouTube + مالی + annotation افزایشی + بازسازی داشبورد.
4. **داشبورد قابل‌دیدن:** `src/reporting/build_dashboard.py` الان HTML می‌سازد ← انتشار ایستا (GitHub Pages) با نمودار روند هفتگی سه پلتفرم، CI، و خط رویدادها.
5. **پایداری:** تست برای پل A→B، annotation و event study (الان فقط ۵ فایل تست)؛ CI با `pytest` + `ruff`.

## ۴. جابه‌جایی و نگهداری داده
- **الان:** حدود ۱۰۰ مگابایت parquet داخل git (`data/raw_harmonized/`، ۳۳۳ هزار رکورد با `text_raw` و `author_hash`). git برای داده‌ی بزرگ و در حال رشد مناسب نیست.
- **پیشنهاد:** داده بیرون از git — Git LFS یا DVC یا GitHub Releases یا Hugging Face Datasets (خصوصی) — و فقط نمونه‌ی دمو در ریپو.
- **ذخیره‌ی تحلیلی:** parquet پارتیشن‌شده بر اساس `platform/project_week` + **DuckDB** برای کوئری سریع (بدون سرور). خروجی Power BI همان جدول‌های `outputs/tables/`.
- **حریم خصوصی قبل از عمومی کردن ریپو:** متن خام کاربران + `author_hash` (C-04: معلوم نیست Salt واقعی بوده یا fallback عمومی). اگر ریپو عمومی است/می‌شود: یا Salt واقعی و hash دوباره، یا حذف `author_hash` از نسخه‌ی عمومی؛ در پست هیچ کامنت کاربری نقل نشود.

## ۵. نمونه‌کار و پست لینکدین
**کد:** README انگلیسی (+ فارسی) با نمودار معماری، quickstart دمو، یک تصویر داشبورد؛ اصلاح یافته‌های بحرانی؛ CI سبز؛ `FINDINGS.md` به‌عنوان «audit report» (نشان‌دهنده‌ی دقت مهندسی).
**پست (چارچوب پیشنهادی):**
1. قلاب: سؤال پژوهشی + مقیاس (۳ پلتفرم، ~۳۳۰ هزار رکورد، فارسی و انگلیسی، ۳۷ هفته).
2. چه ساختم: pipeline داده ← annotation با LLM با سقف هزینه ← آمار با CI و Event Study.
3. **درس اصلی:** audit و پیدا کردن ۴۵٪ داده‌ی جامانده + CIهای خوش‌بینانه، و اینکه چطور درستشان کردم.
4. یک نمودار (روند هفتگی با CI)، لینک داشبورد/ریپو.
5. لحن: روش‌شناسی و یادگیری، **نه ادعای سیاسی**؛ «هم‌راهی زمانی، نه علیت» (همان‌طور که گزارش خودش می‌گوید). موضوع حساس است.
