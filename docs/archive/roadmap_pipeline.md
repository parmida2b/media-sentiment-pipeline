# نقشه راه: Pipeline تحلیل افکار عمومی → تبدیل به ایجنت مکالمه‌ای

**فاز ۱:** ساخت pipeline محکم و config-محور (اولویت الان)
**فاز ۲:** لایه چت‌بات/ایجنت روی همون pipeline (بعداً، اگه وقت موند)

---

## بخش ۱ — چارچوب کلی (قبل از رفتن سراغ جزئیات)

### اصل طراحی
Pipeline باید طوری ساخته بشه که **هیچ فرضی درباره موضوع خاص (جنگ ایران-آمریکا) توی
کد هاردکد نشه**. همه‌چیز از یک فایل `config.yaml` خونده می‌شه:

```yaml
topic: "جنگ ایران و آمریکا"
keywords_fa: ["جنگ ایران آمریکا", "تنش نظامی ایران"]
keywords_en: ["Iran US war", "Iran America conflict"]
date_range:
  start: "2026-02-28"
  end: "2026-08-22"
platforms: ["youtube", "reddit", "twitter", "yahoo finance"]  # ⚠️ منسوخ: تلگرام/توییتر پلتفرم فعال نیستن، ببین docs/decision_log.md ۲۰۲۶-۰۸-۰۴
financial_tickers: ["GC=F", "CL=F", "^GSPC", "^VIX", "BTC-USD"]
sentiment_model: "gemini-2.5-flash"
run_id: "auto"   # پیشنهاد: timestamp خودکار، برای ردیابی هر اجرا
```

### جریان کلی داده (هر مرحله ورودی مرحله بعدیه، مستقل و rerun-پذیر)

```
config.yaml
   │
   ▼
[1] data_collection  → data/raw/*.jsonl (طبق schema.py) + source_advisor_trace.json
   │
   ▼
[2] preprocessing    → data/processed/clean.jsonl + cleaning_report.md
   │
   ▼
[3] classification   → data/processed/sentiment_labeled.jsonl
   │
   ▼
[4] analysis         → outputs/kpi.json + outputs/correlation_report.json
   │
   ▼
[5] visualization     → outputs/charts/*.png + powerbi_theme.json
   │
   ▼
[6] reporting         → outputs/final_report.md (خودکار جمع‌بندی همه‌ی بالا)
```

**قانون طلایی:** هر مرحله فقط از دیسک می‌خونه و فقط روی دیسک می‌نویسه (نه
پاس دادن آبجکت در حافظه بین ماژول‌ها). این یعنی:
- هر مرحله رو می‌شه جدا تست/rerun کرد بدون اجرای کل pipeline.
- اگه یه مرحله وسط کار fail کرد، quota/زمان مراحل قبلی هدر نمی‌ره.
- برای فاز ۲ (ایجنت) هم آماده‌ست، چون ایجنت فقط باید بدونه کدوم فایل رو کجا بذاره.

### مسئولیت ماژول‌ها (بر اساس تقسیم‌کار فعلی تیم)
| ماژول | مسئول | ورودی | خروجی |
|---|---|---|---|
| `config/` | حسین (`config.yaml`) + پارمیدا (`schema.py`) | - | `config.yaml`, `schema.py` |
| `data_collection/` | پارمیدا + حسین | config | raw jsonl + trace |
| `preprocessing/` | پارمیدا | raw jsonl | clean jsonl + گزارش تمیزکاری |
| `classification/` | پارمیدا | clean jsonl | sentiment-labeled jsonl |
| `analysis/` | علی | labeled jsonl + مالی | KPI + correlation/causality |
| `visualization/` | ریحانه | خروجی analysis | نمودارها + تم Power BI |
| `reporting/` | ریحانه | همه بالا | گزارش نهایی خودکار |

## بخش ۲ — جزئیات اجرایی هر مرحله

### ۲.۱ `config/`
- `schema.py` (ساخته شده) — فرمت واحد رکورد.
- `config.yaml` — تنظیمات هر اجرا (بالا نمونه‌ش رو دیدی).
- `config_loader.py` — یک تابع ساده که yaml رو می‌خونه، validate می‌کنه
  (مثلاً `end_date > start_date`)، و به بقیه ماژول‌ها می‌ده.
- **تصمیم مهم:** `run_id` (مثلاً `2026-07-25_run01`) از همین‌جا تولید بشه و
  در تمام مسیرهای خروجی (`data/raw/{run_id}/...`) استفاده بشه. این کار
  باعث می‌شه بشه چند اجرا رو بدون بازنویسی هم مقایسه کرد — برای تست
  فاز ۲ (موضوع جدید) حیاتیه.

### ۲.۲ `data_collection/`
- `youtube.py`, `reddit.py`, `telegram.py` — هرکدوم یه تابع
  `extract(config) -> List[Record]` که طبق `schema.py` خروجی می‌ده.
  ⚠️ منسوخ: تلگرام (و توییتر بالاتر) دیگه پلتفرم فعال نیستن (`docs/decision_log.md`
  ۲۰۲۶-۰۸-۰۴) — فقط YouTube ادامه پیدا کرد.
- `source_advisor.py` (ساخته شده) — پیشنهاد منبع/رویداد + gate تأیید.
- **قانون:** اگه یه پلتفرم fail شد (quota، BAN، خطای API)، بقیه پلتفرم‌ها
  باید ادامه پیدا کنن (try/except دور هر پلتفرم، نه دور کل حلقه).

### ۲.۳ `preprocessing/`
شامل:
- حذف تکراری‌ها (duplicate detection بر اساس `text` + `author`)
- تشخیص و فیلتر بات‌ها (سن اکانت، نسبت فالوور/فالووینگ اگه در دسترسه)
- تشخیص زبان (`langdetect` یا مشابه) و افزودن فیلد `language`
- نرمال‌سازی متن (حذف URL، ایموجی اضافه در صورت نیاز، unicode normalize
  برای فارسی)
- **خروجی اجباری:** `cleaning_report.md` که دقیقاً بگه چند رکورد ورودی،
  چند حذف شد و چرا (تکراری/بات/زبان نامشخص)، چند رکورد نهایی موند. این
  دقیقاً چیزیه که سند به‌عنوان «مستندات روش تمیزکاری» می‌خواد.

### ۲.۴ `classification/`
- `llm_sentiment.py` — batch processing با مدل انتخابی (Gemini Flash یا
  Groq/Llama)، با retry و rate-limit handling.
- **قبل از استفاده کامل:** حتماً روی یه نمونه ۱۰۰-۲۰۰ تایی دستی‌برچسب‌خورده
  اعتبارسنجی بشه (بخش تست پایین‌تر توضیح داده شده).
- خروجی هر رکورد: `sentiment_label`, `confidence`, `model_used`.

### ۲.۵ `analysis/`
- تجمیع هفتگی (resample بر اساس `date`) برای هم‌ترازی با داده مالی.
- محاسبه شاخص‌های KPI: نسبت مثبت/منفی/خنثی هفتگی، حجم تعامل (like/reply)،
  نرخ تغییر هفته‌به‌هفته.
- Correlation matrix بین KPI‌های احساسات و متغیرهای مالی.
- **Granger causality test** (نه فقط همبستگی خام) با توجه به stationarity
  (لازمه قبلش تست ADF/KPSS بشه، وگرنه نتیجه Granger گمراه‌کننده‌ست).
- اگه متغیرهای مالی رابطه معناداری نداشتن (طبق سند این حالت پیش‌بینی شده)،
  باید عوامل جایگزین (رویدادهای سیاسی/رسانه‌ای از `source_advisor`) رو
  به‌عنوان متغیر توضیح‌دهنده اضافه و آزمایش کرد.

### ۲.۶ `visualization/`
- نمودارهای روند زمانی احساسات + متغیرهای مالی روی هم (dual-axis یا
  small multiples).
- `powerbi_theme.json` — پیشنهاد پالت رنگ بر اساس موضوع (مثلاً برای
  موضوع جنگ: پالت خنثی/جدی به‌جای رنگ‌های شاد بازاریابی).

### ۲.۷ `reporting/`
- یک اسکریپت که خروجی همه مراحل بالا رو جمع‌بندی و به `final_report.md`
  تبدیل کنه — شامل جامعه آماری، محدودیت‌ها، یافته‌ها، نمودارها.

### ۲.۸ `pipeline_runner.py`
⚠️ منسوخ/اجرا نشده: این فایل هیچ‌وقت در `src/` ساخته نشد؛ مراحل پایین هرکدوم
جدا و دستی اجرا می‌شن، نه از پشت یک CLI/orchestrator واحد (ببین
`docs/README.md` بخش ۴ — `architecture.md` هنوز TODOئه).
- یک CLI ساده: `python pipeline_runner.py --config config.yaml --stage all`
- پشتیبانی از `--stage <name>` برای اجرای تک‌مرحله‌ای (برای دیباگ/توسعه).
- لاگ ساختاریافته (نه فقط print) — پیشنهاد: `logging` استاندارد پایتون با
  سطح INFO/WARNING/ERROR، ذخیره در `outputs/{run_id}/pipeline.log`.

## بخش ۳ — استراتژی تست و ارزیابی

### سطح واحد (Unit-level)
- تست `schema.py`: رکوردهای ناقص باید توسط `validate_record` رد بشن.
- تست `preprocessing`: با یه نمونه دستی‌ساخته (شامل تکراری، بات، متن خالی)
  چک کن خروجی درست فیلتر می‌شه.
- تست `config_loader`: تاریخ نامعتبر (end < start) باید error بده، نه
  سکوت.

### سطح مدل (Sentiment)
- یه نمونه ۱۰۰-۲۰۰ تایی (نصف فارسی، نصف انگلیسی، شامل کنایه/طعنه) رو
  **دستی** برچسب بزنید (حداقل ۲ نفر از تیم جدا برچسب بزنن، بعد
  inter-annotator agreement با Cohen's kappa بسنجید — اگه توافق پایینه،
  خود raw label هم قابل اعتماد نیست).
- روی همین نمونه، مدل انتخابی رو اجرا کن، accuracy/F1 per class حساب کن.
- **حتماً per-language گزارش بده** (ممکنه مدل روی انگلیسی خیلی بهتر از
  فارسی عمل کنه — این خودش یافته‌ی مهمیه که باید در گزارش نهایی بیاد).

### سطح آماری
- قبل از Granger: تست stationarity (ADF test) روی سری‌های زمانی.
- بعد از همبستگی: تصحیح برای multiple testing (چون چند متغیر مالی رو
  همزمان با sentiment مقایسه می‌کنید، شانس false positive بالا می‌ره —
  Bonferroni یا FDR ساده کافیه).
- Robustness check: نتیجه رو با حذف ۱-۲ هفته پرت (outlier) دوباره تست کن،
  ببین نتیجه پایدار می‌مونه یا نه.

### سطح Pipeline (Integration)
- قبل از اجرای کامل روی کل داده، حتماً یه بار با یه نمونه کوچیک (مثلاً
  ۵۰ رکورد ساختگی) کل `pipeline_runner.py --stage all` رو اجرا کن تا
  مطمئن بشی مراحل به‌هم درست وصلن، قبل از این‌که وقت/quota واقعی رو
  خرج کنی.
- بعد از هر merge روی `main`، یه smoke test سریع (اجرای همین نمونه کوچیک)
  اجرا بشه تا خرابی زودتر دیده بشه.

### سطح `source_advisor`
- روی ۲-۳ موضوع تستی (نه فقط موضوع اصلی) پیشنهادات رو دستی چک کنید که
  آیا واقعاً معتبرن (spot-check لینک‌ها) — چون این مرحله مستقیماً پایه
  انتخاب جامعه آماریه.

## بخش ۴ — مسیر تبدیل به ایجنت (فاز ۲، بعد از پایدار شدن فاز ۱)

**پیش‌شرط:** فاز ۱ باید کامل و end-to-end تست‌شده باشه قبل از شروع فاز ۲.
دلیلش اینه که ایجنت فقط یه لایه UX روی pipeline‌ـه؛ اگه pipeline خودش
پایدار نباشه، دیباگ کردن ایجنت (که خودش عدم‌قطعیت اضافه می‌کنه) خیلی
سخت‌تر می‌شه.

1. **قدم اول — Config Wizard مکالمه‌ای (نه ایجنت کامل):**
   یه چت ساده که فقط سؤالای config.yaml رو از کاربر می‌پرسه (موضوع، بازه
   زمانی، پلتفرم‌ها) و در نهایت همون فایل config رو تولید می‌کنه. هنوز
   منطق تصمیم‌گیری نداره، فقط جمع‌آوری ورودی.

2. **قدم دوم — اتصال `source_advisor` به مکالمه:**
   خروجی `source_advisor.py` (که ساختیم) به‌جای `input()` توی ترمینال،
   از طریق چت به کاربر نمایش داده بشه و تأیید/رد از همون‌جا گرفته بشه.

3. **قدم سوم — مدیریت state مکالمه:**
   باید مشخص بشه state مکالمه (موضوع انتخاب‌شده، تأییدها، مرحله فعلی
   pipeline) کجا نگه داشته می‌شه — ساده‌ترین راه: یک فایل JSON session
   که هر پیام مکالمه بروزرسانیش می‌کنه.

4. **قدم چهارم — مدیریت خطا در سطح مکالمه:**
   وقتی quota تموم شد یا جستجو نتیجه نداد، ایجنت باید صریح و قابل‌فهم
   به کاربر بگه (نه سکوت یا کرش)، و گزینه‌های جایگزین پیشنهاد بده.

5. **قدم پنجم — تست تعمیم‌پذیری (مهم‌ترین تست فاز ۲):**
   دقیقاً طبق بخش امتیازی سند، ایجنت رو با یه **موضوع کاملاً متفاوت**
   (مثلاً «دیدگاه جهانی به سینمای ایران») اجرا کن، بدون تغییر دستی کد.
   اگه به تغییر کد نیاز داشت، یعنی هنوز واقعاً generic نشده.

6. **قدم ششم (اختیاری، اگه وقت موند) — رابط کاربری:**
   یه رابط ساده (مثلاً Streamlit/Gradio chat) روی همون منطق. اولویت این
   خیلی پایین‌تر از قدم‌های بالاست.

## بخش ۵ — مواردی که ذکر نکردی ولی مهمن

- **مدیریت هزینه/quota تجمعی:** یه فایل ساده `usage_log.json` نگه دار که
  هر فراخوانی LLM (چه sentiment، چه source_advisor) رو با تعداد توکن/
  زمان لاگ کنه — هم برای گزارش «چرا این راهکار اقتصادی‌تره» در سند لازمه،
  هم جلوی تموم شدن غافلگیرکننده quota رو می‌گیره.
- **Versioning خروجی‌ها:** هر بار که pipeline اجرا می‌شه، خروجی توی پوشه
  `outputs/{run_id}/` بره نه رونویسی روی قبلی — برای مقایسه نسخه‌ها و
  برای دموی نهایی (که باید نسخه‌ی پایدار و از‌پیش‌تست‌شده نشون بدید، نه
  اجرای لایو ریسکی).
- **Anonymization قبل از دمو:** طبق چیزی که قبلاً گفتیم، `author_display_name`
  رو قبل از نمایش عمومی/دمو حذف یا هش کنید.
- **مستندسازی هم‌زمان با کد، نه آخر کار:** هر ماژول همون لحظه که تموم شد،
  یه پاراگراف توضیح توی `docs/methodology.md` اضافه بشه (مسئول: هرکس
  ماژول خودش رو مستند کنه) — وگرنه روز آخر همه فشار میاد روی ریحانه.
- **آماده‌سازی داده‌ی دمو از قبل:** یه اجرای کامل و پایدار pipeline رو
  از چند روز قبل از ضرب‌الاجل نگه دارید مخصوص ویدیوی دمو، تا اگه چیزی
  در اجرای زنده خراب شد، نسخه‌ی پشتیبان آماده باشه.
